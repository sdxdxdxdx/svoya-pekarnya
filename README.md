# Своя пекарня

Общий учёт закупок, продаж, рецептур, смен, зарплаты, расходов и денежных движений владельцев. Интерфейс работает с телефона и компьютера.

## Архитектура и доступ

GitHub Pages публикует статическое приложение Vite/React. Supabase Auth отвечает за вход по почте и паролю; Postgres хранит общие записи; Edge Function `bakery-api` обрабатывает чтение и изменение данных.

На каждом запросе функция проверяет токен через Supabase Auth `getUser`, подтверждение почты и активную запись в серверной таблице `bakery_members`. Регистрация аккаунта сама по себе не открывает учёт. Браузерные роли `anon` и `authenticated` не имеют прямого доступа к таблицам или RPC записи. Изменения проверяются на сервере; версии записей защищают от перезаписи чужих изменений.

Рабочие справочники, цены, ставки, операции, адреса владельцев и резервные копии хранятся вне публичного репозитория и статической сборки. В браузере сохраняется сессия входа; финансовые записи не дублируются в `localStorage`.

`public/config.json` содержит только URL проекта и ключ `sb_publishable_…`: этот ключ предназначен для публичного клиента и не выдаёт доступ к данным без авторизации. `service_role`, секретные ключи `sb_secret_…`, пароль базы, SMTP-пароль и токены управления нельзя помещать в исходники, `public/`, сборку или GitHub Pages. `SUPABASE_SERVICE_ROLE_KEY` используется только внутри Edge Function.

## Локальная проверка

Нужен Node.js 22.13 или новее; GitHub Actions использует Node.js 24.

```powershell
npm ci
npm test
npm run build
npm run dev -- --port 5174
```

Сборка появится в `dist/`. У приложения установлен базовый путь `/svoya-pekarnya/`; при изменении имени репозитория обновите `base` в `vite.config.ts`. Успешная сборка интерфейса не заменяет проверку входа и сохранения в рабочем проекте.

По умолчанию API разрешает браузерные запросы с `https://sdxdxdxdx.github.io`. Для разработки на порту 5174 предусмотрен серверный флаг `BAKERY_ALLOW_LOCAL_DEV=true`; включайте его только в отдельном тестовом проекте. Локальный интерфейс с рабочим API без этого флага получит отказ по Origin. При другом хостинге нужно также обновить разрешённый Origin в `handler.ts`.

## Первичная настройка Supabase

1. Создайте проект. Один раз выполните `supabase/schema.sql` через SQL Editor в новой базе. Файл создаёт таблицы, ограничения, RLS, закрытые права и атомарную функцию записи; повторно запускать его целиком в существующей базе не требуется.
2. В настройках Auth включите вход по почте/паролю и подтверждение почты. Укажите адрес приложения с завершающим `/` как Site URL и разрешённый Redirect URL.
3. Запишите URL проекта и его **publishable** key в `public/config.json`:

   ```json
   {
     "supabaseUrl": "https://PROJECT_REF.supabase.co",
     "publishableKey": "sb_publishable_REPLACE_WITH_PUBLIC_KEY"
   }
   ```

4. Установите Supabase CLI и проверьте доступные параметры вашей версии. Из корня проекта выполните:

   ```powershell
   supabase --help
   supabase functions deploy --help
   supabase login
   supabase init
   supabase link --project-ref PROJECT_REF
   supabase functions deploy bakery-api --no-verify-jwt
   ```

   `supabase init` нужен только если локального `supabase/config.toml` ещё нет. Флаг `--no-verify-jwt` отключает проверку на шлюзе: сама `bakery-api` обязательно проверяет пользовательский токен и членство на каждом запросе. Не удаляйте эту проверку из обработчика. URL проекта и служебный ключ доступны функции в серверном окружении Supabase.

5. Администратор вручную добавляет разрешённую почту в `bakery_members` через SQL Editor. Например, заменив адрес на нужный:

   ```sql
   insert into public.bakery_members (email, active)
   values ('partner@example.test', true)
   on conflict (email) do update set active = excluded.active;
   ```

   Адрес должен быть в нижнем регистре, без пробелов. Для отзыва доступа установите `active = false`. Это разрешение на работу в приложении; права управления организацией Supabase для него не нужны.

6. Импортируйте рабочие данные только приватным серверным способом, сохраняя идентификаторы, версии, аудит и отметки удаления. Не добавляйте выгрузку в репозиторий. `tests/database.sql` можно выполнить в SQL Editor: его синтетические записи откатываются транзакцией.

Встроенный почтовый сервис Supabase отправляет письма только на адреса участников команды организации и имеет строгие лимиты. Для регистрации и восстановления пароля совладельца настройте **custom SMTP**, а затем выдайте ему членство в приложении. Не расширяйте права управления организацией только ради доставки письма. [Официальные ограничения SMTP](https://supabase.com/docs/guides/auth/auth-smtp).

## Публикация и обновления

В настройках репозитория GitHub выберите Pages → Source → GitHub Actions. Workflow `.github/workflows/pages.yml` при отправке в `main` запускает тесты, собирает приложение и публикует `dist/`.

```powershell
npm test
npm run build
git add README.md app components lib public supabase tests .github package.json package-lock.json index.html main.tsx tsconfig.json vite.config.ts .gitignore
git commit -m "Update bakery application"
git push origin main
```

Перед коммитом проверьте список файлов: резервные копии и приватные данные в него попадать не должны. Повторный запуск публикации доступен через Actions → Publish bakery to GitHub Pages → Run workflow.

Изменения Edge Function публикуются отдельно от Pages:

```powershell
supabase functions deploy bakery-api --no-verify-jwt
```

Workflow Pages не изменяет базу и не развёртывает функцию. Изменения схемы оформляйте отдельным проверенным SQL-изменением с приватной резервной копией перед применением. После обновления проверьте вход, чтение и сохранение из опубликованного приложения; подтверждённая производственная проверка сохранения требует входа владельца.

## Ежедневная работа

- В «Сводке» выберите период отчёта. Закупки и выплаты отражают движение денег, рецептуры и начисленные смены участвуют в расчёте результата.
- В «Закупках» укажите дату, сырьё, количество, единицу и цену. Для упаковки задайте её содержимое, чтобы рассчитывалась стоимость сырья.
- В «Рецептурах» задайте состав на одно изделие и дату начала действия. Если цена или состав неизвестны, сначала уточните их: приложение отмечает неполную себестоимость.
- В «Продажах» внесите магазин и строки накладной. В «Сотрудниках» отдельно учитывайте смены с премиями и фактические выплаты зарплаты.
- Для накладной можно выбрать немедленную оплату, долг или отдельные оплаты по фактическим датам. Выручка относится к дате отгрузки, деньги — к датам оплат. Неоплаченные накладные прошлых дней доступны в разделе долгов на конец выбранного периода.
- Возврат или обмен, удержанный из оплаты либо возвращённый наличными, внесите в «Расходах» с признаком возврата выпечки. Он уменьшит выручку и кассу один раз. Оплаты накладных указывайте до этого отдельного удержания, чтобы не вычесть сумму дважды; расход сырья автоматически не восстанавливается.
- В закупке можно указать точный итог чека: он определит кассу и цену единицы без потери копеек на округлении. Если известна только общая сумма, выберите соответствующий режим; количество и цена единицы останутся неизвестными до уточнения.
- В «Расходах» укажите оплату и при необходимости отдельную дату признания расхода. В «Кассе владельцев» фиксируйте вложения и снятия.
- Справочники архивируются; удалённые операции можно восстановить в настройках. При конфликте версий сохраните нужный ввод, обновите данные и откройте актуальную запись.
- Изменения совладельца подгружаются при возврате в окно и примерно каждые 30 секунд. В настройках скачивайте приватную JSON-копию: она включает удалённые записи. Автоматического восстановления JSON через интерфейс нет.

Если база недоступна после перерыва, владелец проекта должен проверить её состояние и восстановить работу через Supabase Dashboard.
